## 2편에서 Gemini로 해결했는데, 왜 다시 로컬로?

2편에서 캐릭터 문제를 **Gemini(Nano Banana Pro)** 로 풀었습니다. 정면 하나만 잘 뽑고 나면 뒷모습·측면·배경 제거까지 알아서 해줬죠. 그런데 결론이 이랬어요.

**"자동화하려면 유료 API. NPC 50명이면 API 호출 200번. 비용이 만만치 않다."**

그래서 이번 편의 질문은 이겁니다.

**"유료 API 없이, 그리고 무거운 GPU 없이 스프라이트 시트를 양산할 수 있을까?"**

결론부터 말하면 — **됩니다.** 100% 완벽하진 않고 리터치도 조금 들어가지만, 로컬에서 파이프라인이 돌아갑니다.

![최종 결과 — 4방향 스프라이트(정면·측면·후면·측면)](/assets/images/2026/09/08/rpg3/01-sprite-sheet-final.png)

이 결과를 어떻게 만들었는지 순서대로 정리합니다.

## 픽셀아트 전용 모델부터 — Pixel Art Sprite Diffusion

일단 **픽셀아트에 특화된 SD 계열 모델**을 찾았습니다. Civitai에서 다운로드 5.4K, 좋아요 462인 **Pixel Art Sprite Diffusion**을 잡았어요.

![Pixel Art Sprite Diffusion — Civitai 페이지, Safetensors 배포](/assets/images/2026/09/08/rpg3/02-pixel-art-sprite-diffusion.png)

이 모델의 장점은 **처음부터 스프라이트 시트 형태로 결과가 나온다**는 것. 별도 후처리 없이 4방향 정도가 한 이미지에 얹혀 나옵니다.

![Pixel Art Sprite Diffusion — 4프레임 스프라이트 형태로 출력](/assets/images/2026/09/08/rpg3/03-pixel-model-result-orange.png)

**하지만 한계가 있었습니다.** 이 모델이 학습한 스타일이 한정적이라, 원하는 캐릭터 콘셉트를 자유롭게 뽑기 어려웠어요. 특정 서양 게임 스타일에 가까운 결과만 나오는 느낌이랄까요. 우리가 원하는 **일본식 SD(Super Deformed) 픽셀아트 RPG 캐릭터**로 가려면 다른 모델과 병행이 필요했습니다.

## 기본 모델로는 픽셀 감이 나는 캐주얼 모델을 선택

그래서 실제 **기본 모델**로는 다른 SD 계열 체크포인트를 썼습니다. 픽셀아트 뉘앙스는 있지만 좀 더 자유로운 스타일을 뽑을 수 있는 모델이었어요. 정확한 이름은 지금 다시 찾지 못했는데, 결과물의 느낌은 이런 식입니다.

![기본 모델 결과 — 정면 캐릭터 1](/assets/images/2026/09/08/rpg3/04-base-model-front-blue.png)

![기본 모델 결과 — 정면 캐릭터 2](/assets/images/2026/09/08/rpg3/05-base-model-front-black.png)

정면 하나는 이 모델로 뽑을 수 있게 됐습니다. 문제는 **여기서부터**입니다.

## 캐릭터 일관성 문제 — IPAdapter로 참조 이미지 강제

같은 프롬프트로 다시 뽑으면 얼굴이 바뀝니다. 옷이 바뀝니다. **후면 뷰를 만들려고 하면 아예 다른 사람이 나옵니다.** 2편에서 SD가 잘 안 됐던 그 문제 그대로예요.

이걸 해결하려면 "기준 이미지를 참조로 강제하는" 장치가 필요합니다. **IPAdapter(Image Prompt Adapter, IPA)**가 그 역할을 합니다.

원리는 이렇습니다. 텍스트 프롬프트만 주는 게 아니라 **정면 기준 이미지 하나를 함께 넣어서, "이 사람 스타일·색·의상 유지"라는 조건을 모델에 강제**합니다. 그러면 뒷모습·측면을 뽑을 때도 얼굴색·머리색·의상 톤이 유지돼요.

Gemini에게 이미지 붙여넣고 "이 캐릭터의 뒷모습" 시키던 것과 비슷한 아이디어를, 로컬 SD 파이프라인에서 재현하는 겁니다.

![IPA 활용 — 참조 이미지에 지시문 붙여서 후면 생성](/assets/images/2026/09/08/rpg3/08-ipa-chat-prompt.png)

![IPA 결과 — 망토로 몸을 덮은 뒷모습이 참조 이미지 스타일 유지](/assets/images/2026/09/08/rpg3/09-ipa-cloak-back-result.png)

**IPA만으로는 부족했습니다.** 스타일과 정체성은 유지되는데 **포즈**가 제멋대로 나왔어요. "뒷모습"이라고 해도 각도가 안 맞거나, "걷는 자세"가 그냥 서 있는 자세로 나오거나.

## 포즈는 OpenPose로 강제 — 그리고 결국 코드로

포즈를 제어하려면 **OpenPose(오픈포즈)** ControlNet을 얹어야 합니다. 스켈레톤(관절 위치)을 그림처럼 그려서 넣으면, 모델이 그 뼈대 위에 캐릭터를 얹어 그려주는 방식이에요.

처음엔 **OpenPose 에디터 툴**로 스켈레톤을 직접 만들었습니다. 3D 인체 모형을 돌려가며 관절을 잡고, 정면/측면/후면 4방향 스켈레톤을 뽑는 식이었어요.

![OpenPose 에디터 — 3D 스켈레톤을 돌려가며 4방향 포즈 제작](/assets/images/2026/09/08/rpg3/06-openpose-tool-ui.png)

한 캐릭터 뽑는 데 이걸 4번씩 해야 한다는 게 문제였습니다. NPC 50명이면 200번. **API 비용 피하려다 노가다 지옥으로 들어가는 상황**이었죠.

**그래서 코드로 넘어갔습니다.** OpenPose 스켈레톤은 결국 **관절 좌표의 나열**이에요. 정면·측면·후면·다른 측면의 관절 좌표 세트를 함수로 만들고, 파이썬으로 스켈레톤 이미지를 직접 렌더링했습니다. 툴로 하던 4번의 클릭 작업이 함수 호출 한 번으로 줄었어요.

![OpenPose 컨트롤로 뽑은 측면 뷰 — 포즈는 잡히지만 실루엣 문제 발생](/assets/images/2026/09/08/rpg3/07-openpose-result-side.png)

## Canny Edge로 실루엣·윤곽 잡기

IPA로 스타일 잡고 OpenPose로 포즈 잡아도 **한 가지가 더 흔들렸습니다.** 캐릭터의 **실루엣·의상의 굴곡·소품의 위치**요. 예를 들어 망토 라인이 프레임마다 다르게 나오거나, 무기 위치가 어긋나거나.

그래서 세 번째 컨트롤넷으로 **Canny Edge**를 붙였습니다. 참조 이미지에서 엣지(윤곽선)를 추출해서 그걸 조건으로 강제하는 방식이에요.

![Canny Edge 결과 — 참조 이미지에서 추출한 픽셀 단위 엣지](/assets/images/2026/09/08/rpg3/10-canny-edge.png)

**엣지 이미지 자체는 사람 눈엔 이상하게 보입니다.** 픽셀아트에서 뽑은 Canny라 얇은 사각형 선들이 어지럽게 나와요. 그런데 모델은 이걸 잘 이해합니다. "이 실루엣 안에서 그려라"라는 강한 제약이 되니까요.

**최종 조합**은 이렇게 3중 컨트롤넷입니다:

| 컨트롤 | 역할 |
|---|---|
| **IPAdapter** | 캐릭터의 정체성·스타일·색상 유지 |
| **OpenPose** | 포즈(4방향·걷기 자세) 강제 |
| **Canny Edge** | 실루엣·의상 라인·소품 위치 유지 |

셋을 다 얹으면 이 편 처음에 봤던 **4방향 스프라이트**가 나옵니다.

## 리터치는 최소한만

솔직히 **100% 완벽하진 않습니다.** 프레임마다 얼굴이 살짝 다르거나, 뒷모습에서 팔 길이가 어색하거나, 걷기 프레임 사이 연속성이 어긋나는 경우가 있어요.

그래서 **최소한의 리터치**가 여전히 들어갑니다. 마감 픽셀 몇 개 고치는 정도예요. 다만 이게 "AI가 뽑은 걸 사람이 처음부터 다시 그리는" 수준은 아닙니다. **틀만 잡히면 손볼 곳이 눈에 띄게 줄었다**는 게 이번 편의 성과입니다.

리터치까지 자동화하려는 시도도 병행 중이에요. **Claude Code로 픽셀 후처리 스크립트를 짜서** 반복 노가다를 줄이는 방향입니다. 결국 "AI로 만든 걸 AI로 다듬는" 구조로 가고 있습니다.

## 다음은 LoRA — 진짜 양산 체제

여기까지가 오늘 도착한 지점입니다. 그런데 여전히 문제 하나가 남아요. **매번 IPAdapter 참조 이미지를 준비해야 한다**는 것. 같은 캐릭터 하나 뽑는 건 되는데, **"이 게임의 아트스타일"** 자체를 학습시켜서 새 NPC를 프롬프트만으로 뽑고 싶어지죠.

그래서 다음 단계는 **LoRA(Low-Rank Adaptation) 학습**입니다. 지금까지 뽑아둔 캐릭터 결과물을 데이터셋으로 삼아, "우리 게임 스타일" LoRA를 하나 만드는 거예요. 성공하면 IPAdapter 없이도 스타일이 유지되고, 프롬프트만 바꿔서 새 NPC를 양산할 수 있게 됩니다.

이건 다음 편에서 다뤄보겠습니다.

## 정리 — 유료 API 대신 3중 컨트롤넷

이번 편의 핵심을 다시 모으면:

- **픽셀아트 전용 모델**(Pixel Art Sprite Diffusion)은 처음부터 스프라이트 형태로 결과가 나오지만 스타일 제약이 있음. 기본 모델과 병행 필요.
- **캐릭터 일관성**은 IPAdapter로. 참조 이미지를 강제하는 방식이 SD 계열에서 가장 확실.
- **포즈 통제**는 OpenPose ControlNet. 툴로 시작해서 결국 파이썬으로 스켈레톤 좌표를 코드 생성.
- **실루엣·라인 유지**는 Canny Edge ControlNet.
- **API 대신 3중 컨트롤넷**(IPA + OpenPose + Canny)으로 로컬 GPU에서 파이프라인이 돌아감. Gemini API를 대체할 수 있는 수준.
- **리터치는 여전히 필요**하지만 대폭 줄었고, 그마저도 코드로 자동화 시도 중.
- **다음 단계는 LoRA** — 게임 아트스타일 자체를 학습시켜 프롬프트만으로 새 캐릭터 양산.

## 시리즈 흐름 정리

- **1편**: SDXL Turbo로 맵·SAM v3로 마스크. 캐릭터는 실패.
- **2편**: Gemini(Nano Banana Pro)로 캐릭터 일관성·후면/측면 뷰 해결. 자동화는 API 비용 문제.
- **3편(이번)**: **유료 API 없이 로컬에서 스프라이트 시트 파이프라인** 완성. IPA + OpenPose + Canny 3중 컨트롤넷.
- **4편(예고)**: LoRA로 게임 스타일 학습 → 진짜 양산 체제로.
